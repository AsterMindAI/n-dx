0. THE ONE-PARAGRAPH VERSION
--------------------------------------------------------------------------------
n-dx pays a hosted LLM for every inference. We set out to replace those calls
with free local ELMs. Of 22 LLM call sites, only 2 are ELM-replaceable; the
other 20 generate prose and stay hosted. Team Nolan took the larger of the two
(sourcevision archetype classification). We have since: fixed a real
classification bug, built a 324-row labelled corpus, found and fixed a defect
that made the project unable to measure its own objective, and priced what an
LLM call actually costs. The ELM itself has NOT been built. The case for it is
narrower than we started with, but it now rests on measurements instead of
assumptions.

--------------------------------------------------------------------------------
1. SCOPE OF THE OPPORTUNITY                              [measured by Jam, TN-J1]
--------------------------------------------------------------------------------
Every LLM call routes through two chokepoints -- callClaude
(sourcevision/analyzers/claude-client.ts:145) and spawnClaude
(rex/analyze/llm-bridge.ts:135) -- plus hench's agent loop.

  Total LLM call sites surveyed ................. 22
  ELM-replaceable ................................ 2
  Generate prose, must stay hosted ............... 20

The dividing line is output shape. An ELM emits a label from a closed set. It
cannot write prose. That is the answer, not a limitation to engineer around.

The two candidates:
  Path B  sourcevision archetype classification  classify.ts:404   17 classes
  Path C  rex granularity assessment             reason.ts:1481     3 classes

Two corrections found during the survey, both worth keeping:
  - "rex placement" is ALREADY deterministic (core/move.ts:91,
    core/structural.ts:125; rex/src/recommend/ has zero LLM calls). There is no
    token spend there to remove.
  - enrichClassificationsWithLLM is the classification path despite its name.
    The enrich*.ts files are generation and are NOT replaceable. Easy to
    conflate.

4. THE MEASUREMENT DEFECT                             [Butter, TN-J3 -- FIXED]
--------------------------------------------------------------------------------
The project existed to reduce token usage and could not measure token usage.

EVIDENCE, AND WHY THE ORIGINAL FILING WAS INSUFFICIENT.
All 6 .hench/runs/*.json record tokenUsage {"input":0,"output":0}, on runs of
21, 47, 53 and 60 turns. But all six are dated 2026-02-04, and
event-accumulator.ts -- the code that accumulates -- landed 2026-04-21
(0269cf75). The evidence predated the mechanism by 2.5 months. It established
"nobody has measured since February", not "the counter is broken".

THE FRESH MEASUREMENT (A1). sourcevision analyze AsterMind-CE --full, run to
completion:
    manifest.tokenUsage = { calls: 9, inputTokens: 0, outputTokens: 0 }
Nine real LLM calls on current code, both token counters at zero. So it WAS a
live defect -- just not provable from the February files.

ROOT CAUSE. accumulateTokenUsage increments `calls` BEFORE the usage guard
(`aggregate.calls++;` then `if (!usage) return;`), so calls:9 with zero tokens
proves it was handed undefined nine times. It was: parseCliTokenUsage read only
TOP-LEVEL fields --
    envelope.input_tokens ?? envelope.total_input_tokens
-- while the current CLI NESTS them under `usage`. Verified by dumping a real
envelope (CLI 2.1.237); its top-level keys are:
    api_error_status, duration_api_ms, duration_ms, fast_mode_state, is_error,
    modelUsage, num_turns, permission_denials, result, session_id, stop_reason,
    subtype, terminal_reason, time_to_request_ms, total_cost_usd, ttft_ms,
    ttft_stream_ms, type, usage, uuid
Not one of the four fields the parser looks for is present.

The tell that this was a stale assumption rather than a design choice:
parseStreamTokenUsage, IN THE SAME FILE, already handled the nested shape and
documented it as "some CLI versions". Only the non-stream path was left behind.

FIX. Mirror the stream parser's nested fallback, top-level still winning so
older flat envelopes are unaffected. Test written first and WATCHED GO RED
(3 failures, "expected 'unavailable' to be 'complete'"), then green.
  token-usage.test.ts ....... 51/51 (47 pre-existing)
  pnpm typecheck ............ clean, all 6 packages
  live callClaude ........... before: tokenUsage undefined
                              after:  {input:2, output:4,
                                       cacheCreationInput:22617,
                                       cacheReadInput:23331}

        Path B ceiling on AsterMind-CE:  3 of 9 invocations = 33%

        At the ADR's 30% kill criterion:  1 of 9

(c) SAVINGS ARE LUMPY, AND SMALL WINS CAN HONESTLY REPORT ZERO.  [Jam]

        Repo          files needed before the FIRST call is avoided   hit rate
        n-dx                                                     15       5.9%
        AsterMind-CE                                              9      13.0%

    Demonstrated by Jam's own Step 1: it reclassified 4 real files -- a genuine

    40% both yield 4) -- that is the lumpiness, not an arithmetic error.

7. THE PROVIDER PROBLEM -- AND WHY IT IS NOT AN N-DX BUG      [Butter, TN-B2]
--------------------------------------------------------------------------------
~95% of a classify call is cache overhead, not our prompt. The obvious worry was
that n-dx spawns a full agent harness and lets it loop. MEASURED, ON A REAL
CLASSIFY PROMPT:

        num_turns = 1

n-dx does the right thing: one prompt, one turn. It passes only
    -p -  --output-format json  --model <model>
(cli-provider.ts:124-129). There is no agent loop to remove.

THE OVERHEAD IS INHERENT TO USING THE CLAUDE CODE CLI AS A COMPLETION BACKEND.
The CLI loads its own system prompt and tool definitions as cache-creation on
every invocation (45,967 tokens on a cold cache). That is a property of the
backend, not a defect in n-dx, and it exists because THIS MACHINE HAS NO API KEY
(ANTHROPIC_API_KEY, CLAUDE_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY and
GOOGLE_API_KEY are all unset), so llm-client falls back to the CLI provider.
n-dx already ships api-provider.ts for the API path.

>>> CONSEQUENCE THAT AFFECTS EVERY SAVINGS NUMBER WE WILL EVER PUBLISH <<<

    What an avoided call saves depends ENTIRELY on the backend:

        CLI backend (no API key) ..... ~49,000 - 54,000 tokens saved per call
                                       (was quoted as 53,553-267,952; corrected
                                        2026-08-27, see section 5)
        API backend (with key) ....... ~2,700 - 13,700 tokens saved per call
                                       (prompt + completion only -- the 5.12%)

    THE SAME ELM SAVES ROUGHLY 20x MORE ON THE CLI THAN ON THE API.

Any published figure must therefore state which backend it assumes. A number
measured on the CLI will substantially overstate the benefit for an API user,
and understate nothing -- but it is not the same number.

The only n-dx-shaped residue, and it is UNMEASURED and therefore NOT CLAIMED:
n-dx passes no tool-restriction flags to the CLI. Whether that would shrink the
harness is untested. It is the one lever on our side; everything else here is a
provisioning question.

Also concrete and free: total_cost_usd is in EVERY envelope and llm-client never
reads it. CompletionResult (types.ts:82-87) carries only text and tokenUsage.
The vendor hands us the dollar figure and we discard it.

10. OPERATIONAL GOTCHAS EARNED THE HARD WAY
--------------------------------------------------------------------------------
  * analyze-phases.ts IS INVISIBLE TO GREP. Two raw NUL bytes at offsets 16345
    and 16374, deliberate, committed. `file` reports it as data, so grep exits 1
    and prints NOTHING -- silence, not an error. Every repo-wide grep has a hole
    in exactly the file that wires the analyze pipeline. Use python3, grep -a,
    or rg --text. Decision (Nolan, 2026-08-11): leave the bytes alone.  [Jam]
  * --fast GATES TWO PATHS, not one. Dropping it to get classification labels
    also switches on phase-4 zone enrichment, the expensive generation path.  [Jam]
  * RULE FIXES ARE INVISIBLE WITHOUT --full. Incremental mode reuses cached
    archetype:null (classify.ts:99-110; only --full bypasses it,
    analyze-phases.ts:210). Jam nearly recorded a working fix as ineffective.
    User impact: anyone upgrading for better rules sees nothing until a full
    re-analysis. Filed TN-J6.  [Jam]
  * DO NOT STAGE ANYTHING IN THE SESSION SCRATCHPAD. /private/tmp reaped a
    corpus clone mid-session, leaving a directory husk and a silent
    "0 files cataloged" run that looked exactly like a regression. Durable
    clones live in ~/n-dx-elm-corpus/.  [Jam]
  * pnpm test STOPS AT THE FIRST FAILING PACKAGE
    (ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL), so while a rex timing test flakes it
    NEVER REACHES tests/e2e/ AT ALL. Two runs reporting 1991 and 1996 tests were
    different SUITES, not different results. Use `npx vitest run tests/` at the
    root for the architecture tests.  [Jam]
  * A WORKTREE DOES NOT ISOLATE `analyze <other-repo>`. Isolation is
    per-checkout; --full writes .sourcevision/ into the TARGET repo, which may
    be a shared corpus clone outside both checkouts. Claim it.  [Butter]
  * .hench/runs/ IS GITIGNORED (.gitignore:5) YET THE SIX FILES ARE TRACKED --
    committed before the rule landed. So they appear in every worktree, and any
    NEW run will not commit. Fresh evidence needs a deliberate fixture.  [Butter]
  * ELM LIBRARY: charSet is interpolated UNESCAPED into a RegExp character
    class, so a literal '-' must come LAST or it throws. Text training requires
    useTokenizer:true. npm latest is 3.0.0 and the repo pins ^3.0.0; v4 is
    tagged on GitHub but UNPUBLISHED and breaking -- do not chase v4.

13. PHASE 1 AND 2 OF THE TIER -- WHAT TUNING ACTUALLY BOUGHT   [K2, TN-J25/J27]
--------------------------------------------------------------------------------
Added 2026-08-28 by K2, taking over Path B implementation from Jam per
K2-HANDBOOK.md. Bar pre-registered at f4a06175 BEFORE any model ran; the
adoption rule (mean +1.5pp AND >=7 of 9 paired runs) was fixed in that commit.
Artifacts: scripts/elm-architecture-sweep.mjs, scripts/elm-operating-point.mjs,
and their JSON under scripts/data/.

  MEASURED   Activation is a lever and nobody had swept it. tanh 64.6% vs
             relu 60.6% -- +4.0 pp on 9 of 9 paired runs, 5-fold CV on the
             TRAIN split only, gold set untouched. gelu ties (64.59 vs 64.64).
  MEASURED   ridgeLambda is NOT a lever: 60.2-60.8% across 1e-4..1e-1,
             collapsing only at 1e0. This was the sweep the plan had the
             highest prior on.
  MEASURED   Stacked voting over 5 seeded ELMs LOSES 2.8 pp. RBF kernels lose
             at every gamma. Linear KernelELM clears the bar (+3.0 pp, 7 of 9)
             but is beaten by tanh.
  MEASURED   RBF's default gamma is degenerate on this feature space: 1/D =
             5.9e-4 against mean ||x-z||^2 = 1.86 gives K(x,z) ~ 0.999 for
             EVERY pair -- an all-ones Gram matrix. Default-gamma RBF scores
             33.9%; gamma=0.5 on identical data scores 60.8%. 27 pp from one
             default. This was predicted in a committed pre-registration
             addendum BEFORE the run, from the feature space alone.
  MEASURED   Abstention's coverage ceiling is STRUCTURAL. It answers only on
             non-service/utility predictions, and non-S/U is 26.2% of the
             corpus, against the 29.4% coverage that 3-of-9 calls requires on
             n-dx. Measured coverage 25.6% -- within half a point of its own
             ceiling. No model and no precision can close that gap.
  MEASURED   B+su (abstention + top 10% most-confident service/utility) reaches
             32.9% coverage, 75.1% vs the LLM's 74.1% on the same files, and
             3 of 9 n-dx calls. Both bars met in the mean.  ** DEV ONLY. **
  MEASURED   The LLM's errors ARE directional off the service/utility axis. On
             the 24 held-out files whose truth is not S/U it makes 7 errors and
             6 collapse a minority class INTO service/utility. `utility` is the
             teacher's sink for uncertainty. The plan's "noise is random"
             finding is correct on the axis it examined and does not
             generalise to the axis abstention operates on.
  NOT KNOWN  How often the teacher's prompt carries partial algorithmic signals
             the ELM never sees (TN-J26). classify.ts:499-503 appends them
             whenever ANY signal matched, independent of the threshold that
             made the file unclassified -- but classifications.json overwrites
             the pre-LLM evidence with the LLM's own returned reason, so it
             cannot be recovered from any committed artifact. Stated as
             unquantified rather than estimated, on purpose.

THE DENOMINATOR IS NOT COSMETIC. S1 says "on the same files"; the evidence used
to adopt abstention compared a hand-picked subset against the LLM's GLOBAL
average. Under the global denominator 12 of 18 operating points pass. Under the
one S1 actually specifies, on the same model, 0 of 18 do. Same table, same
seeds, different question.

14. THE NEAR-MISS -- K2's OWN ERROR, REPEATED ONE ITERATION LATER   [K2]
--------------------------------------------------------------------------------
Recorded here rather than smoothed over, because section 12 exists for exactly
this and because the guard that caught it is the transferable part.

My first Phase 2 run used activation "relu". Phase 1 had already adopted tanh.
That run returned 0 of 18 designs beating the LLM, and I had drafted an ADR

This is precisely the hiddenUnits:256 mistake -- a verdict on an arbitrary
untested default, mistaken for a verdict on the approach -- committed by the
person brought in to correct it. What caught it was not judgement. It was the
pre-registered rule that Phase 2 runs the model Phase 1 adopted.

The pattern worth carrying: TWO OF THE THREE LARGEST EFFECTS FOUND ON THIS
PROJECT WERE DEFAULTS NOBODY CHOSE. hiddenUnits 256 (worth +12 pp) and relu
(worth +4 pp) were both inherited from the first script written and never
named as decisions. Before tuning anything, list what the code is choosing on
your behalf.

OPERATIONAL: the full sweep was OOM-killed on the voting config (8 GB machine,
9 GB swap in use, a second job running) and EXITED 0 WITH AN EMPTY RESULTS
TABLE -- indistinguishable from a clean early exit. The vectorizer cache had
been accumulating 3 fold-seeds x 5 folds x 3 vocab caps = 45 dense matrices.
Now bounded to one cap. Do not run two of these concurrently on this machine.

11. HOW WE WORK -- the measurement contract
--------------------------------------------------------------------------------
ADR-2026-08-23-butter-savings-measurement-contract.md (Proposed), accepted by
Jam in full for Lane B:

  1. THE AVOIDED INVOCATION IS THE UNIT OF ACCOUNT. Tokens and dollars are
     derived from measured per-call cost, never from prompt-token arithmetic.
  2. ONE INSTRUMENT, ONE OWNER. Path A measures and publishes; Path B quotes.
  3. EVERY FIGURE CARRIES ITS METHOD: repo, commit, command, seed, baseline,
     binary, date, and the committed script that produced it.
  4. MEASURED AND EXTRAPOLATED ARE LABELLED IN THE SAME SENTENCE AS THE NUMBER.

Rule 2 exists because this project has already chased a wrong baseline through
multiple documents twice (5.9% -> 19.6% -> 38.0%). Two independently-derived
numbers is not a hypothetical failure mode here.
