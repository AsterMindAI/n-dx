Should we ship the ELM?

We tried to replace expensive AI calls with a tiny, cheap machine‑learning model that labels source files. The mechanism now works. The classifier does not — and even if it did, it would save less than a change that costs nothing. It is 50–70× faster, which is the one argument that survives.

Summary

Three reasons, any one disqualifying

01

It isn't accurate enough

52–67% agreement with the AI it would replace, on a codebase it has already studied. On an unfamiliar one, no better than guessing the single most common answer.

02

It can't tell when it's wrong

The whole design depends on the model saying “I'm unsure, ask the expensive AI.” Measured ability to do that: AUC 0.595, where 0.50 is a coin flip.

03

A free alternative beats it

At its only trustworthy setting it saves roughly four cents a scan. Changing one configuration number saves 8× more, with zero accuracy cost.

The strongest argument against this recommendation The ELM is 50–70× faster — 14 seconds against 10–17 minutes for the same files. That is real, measured, and it is not a cost argument. If anyone waits on a scan, that changes the conversation. See Speed below.
Background

What the tool does

n‑dx scans a codebase and labels every file with its architectural role — one of 17 archetypes like service, utility, component, route-handler.

Those labels are not decorative. Each archetype carries threshold multipliers: a file labelled component gets twice the tolerance before an oversized function is flagged, and findings are explicitly downgraded to “info” based on archetype. The labels also feed the AI‑readable summary that Claude reads when working in the repo.

How labelling works today — n‑dx, 683 source files
PassMethodFilesCost
1 · RulesPattern-match the file path428Free

A detail most people get wrong The rule pass is effectively path‑only. Of its 75 signals, 40 match the filename and 34 match the directory. One reads export names. One signal type is a stub that always returns nothing. It never opens a file.

What an ELM is

An Extreme Learning Machine is a deliberately simple neural network. Its internal layer is filled with random numbers that are never trained — only the final output layer is fitted, in one mathematical step.

It trains in milliseconds and costs nothing to run. But it does no feature learning: it can only draw straight lines through whatever numbers you hand it. The quality of the input does 100% of the work.

The proposed design

The ELM answers what it is confident about; everything else falls through to Claude, whose answers then become new training data. Like a junior sorter handling easy mail and passing anything uncertain to the expert.

It is a sound design. It depends entirely on the junior knowing when they are unsure.

Findings

Six findings, in the order we found them

01

Every prior positive result measured the wrong files

Four confident numbers had been published: 100% accuracy at 59% coverage, 97% at 42%, an independent reproduction, and a 90.6% cross‑validation. All were real. All measured files that already had rule‑pass signal.

The rules run first and take everything they can label. What reaches the ELM is, by definition, the files where path matching already failed. Every result above measured performance on files that never needed the ELM.

All 263 leftover files produced an identical, all‑zero input. The ELM stage resolved zero files, always — not from bad tuning, but structurally.
02

Reading file contents fixed the mechanism

Nothing in this pipeline had ever read a file's contents — only its path. Adding that was the substantive change, and it worked.

This breaks the architecture, not the tuning. “Send the uncertain ones to Claude” requires knowing which ones are uncertain. It doesn't — so raising the bar rejects a near‑random slice: you pay for the AI calls anyway and keep most of the wrong answers.

A partial fix: train 15 copies with different random seeds and count how many agree. That produces a genuinely usable curve — and also the trap.

05

The obvious excuse was tested and eliminated

Another team found their version failed because of a starved training set, not bad features — fixing that took their score from 21.6% to 47.2%. Our model trained on one codebase, 186 examples, where two labels held about 200 of 255 rows. The same suspicion applied.

So we cloned all nine corpus repositories at exact pinned commits — 2,195 examples, 100% with file contents available — and retested.

  • More data: +10.8 points. Real, and understated — the bigger set adds two harder categories and it improved anyway.
  • Bigger model: −6.2 points, and 100× slower (8 minutes vs 4 seconds). Copying the other team's certified model size actively hurt, because theirs is matched to a different input shape.
  • Still loses to the sticky note. 41.2% against 44.2%, within statistical noise of parity.
The most plausible objection — “you just didn't give it enough data” — was tested with 7.6× more data. The conclusion didn't change.
06

Wrong labels have a real cost

A file mislabelled component inherits twice the tolerance for oversized functions, so a genuine problem gets quietly downgraded to “info”. The AI‑readable summary also describes those files wrong to the next agent that reads them.

At the setting that saves meaningful money, roughly 67 of 255 files get a different label than Claude would have given.

The mechanic that decides everything Calls are batched at 30, so savings are step‑wise, not gradual. Answering 5% of files saves zero calls — 243 files still needs 9 calls. You need about 11.8% coverage to save the first one.

That inverts the usual instinct. A cautious, high‑accuracy, low‑volume gate is worth nothing here. To save money the model must answer in bulk — exactly where it is least accurate. The economics and the quality pull in opposite directions.

The nesting that shrinks “1 of 9” further

  1. 1 of 9 is 11% of the classify pass.
  2. One scan is about 11 AI calls — 9 classify plus 2 zone‑enrichment. Zone enrichment writes prose; an ELM picks from a fixed list and fundamentally cannot do it.
  3. A scan is one command. The agent that reads and writes real code was identified as “likely the majority of token spend”. The ELM touches none of it. Only 2 of 22 AI call sites are replaceable this way.
The measurement nobody has made The share of the total bill that the classify pass represents has never been measured. It is the number that decides whether any of this matters, and it is cheap to get.

Needs testing, not just shipping
  • A failed 255‑file batch is costlier to retry than a failed 30‑file one — up to three attempts.
  • Claude may label less accurately with 255 files in one prompt than 30. Unknown, and directly measurable against labels we already have.
  • 255 answers might approach the output limit. The reason field each answer carries has no external consumer — it is only recycled into retry prompts — so it could be dropped.

The Obvious Question

Would more training data fix it?

Data is the only lever that moved the number meaningfully (+10.8 points for 7.6× more). So it deserves a real answer rather than a shrug. The answer splits in two.

The ELM cannot beat the LLM on accuracy at any data volume — because the LLM is its teacher.

Every training label came from Claude. A student trained on a teacher's labels converges toward agreement with that teacher, not toward truth. More data approaches 72.3%‑correct behaviour asymptotically; it cannot pass it. That is a supervision problem, not a data problem.

Two things make it worse rather than merely flat:

  • The teacher's errors are directional. Six of seven collapse a rare label into service/utility. Random noise averages out with scale; systematic bias gets learned more confidently.
  • The ELM does no feature learning. More data fits the readout better; it cannot discover a feature we did not hand‑encode. That is the LLM's real advantage — representation learning, not data volume — and it is the gap data cannot close.

Clearing the majority baseline costs about $5 and an afternoon. That is the most actionable finding in this report — we are 2× away from passing the bar this project has been failing, and not knowing is cheaper to fix than to argue about.

But accuracy is not the binding constraint

The gate does not need the ELM to be as good as the LLM. It needs the ELM to know which of its answers to trust — answer those, defer the rest. A 60%‑accurate model that knew which 60% would be an excellent gate. That is calibration, and it scales worse.

A gate you would actually ship needs roughly half a million labelled files — every one labelled by the teacher whose ceiling it is stuck under anyway.

Two points, log-linear — read as directional, not predictive Both tables extrapolate from the only two measurements we have, and ignore every ceiling named above. Learning curves usually flatten sooner than this. The numbers are here to size the bet, not to promise an outcome.

And a caveat on our own earlier result: the finding that 4096 hidden units hurts was measured at 1,935 rows, where it overfits. Capacity and data interact — at 65,000 rows a bigger model might well win. If anyone scales the data, that sweep has to be re‑run. That result does not transfer to a different data regime.

What this means

The realistic best case is “nearly as accurate, 50–70× faster, free per call.” That is a legitimate product. It simply is not better than the LLM, and it cannot be while the LLM writes the answer key.

To break that ceiling you need a different answer key — human labels, consensus across several models, or the rule pass's own high‑confidence output as ground truth. That converts the project from compress the LLM into learn the task, which is a different and more expensive proposition.

Analysis

Why this is structurally hard

Five reasons this was not simply a tuning failure. Three are measured; two are reasoned inference, marked as such.

  1. The gate gets an adversarially‑selected population measured — only files where the best cheap signal already failed.
  2. You can't beat your teacher, and this teacher's errors are directional measured — 72.3% correct against an 85.4% human ceiling, and it saw more context than the student does. Its errors aren't random: utility is its dumping ground, and 6 of 7 errors collapse a rare label into service/utility. Random noise averages out; directional bias gets amplified — which is exactly what we see.
  3. “Archetype” may be partly repo‑relative inference — if the right label depends on a project's conventions, cross‑codebase transfer is partly an ill‑posed question.
  4. The gate starves its own teacher inference — files the ELM answers never reach Claude, so they never produce new training examples. The training set only ever grows from the ELM's failures. The better it performs, the more biased its future training data becomes.
  5. The ELM does no feature learning structural — random layer, one‑step fit. The representation does all the work.
Not Dead

What would have to change

The accuracy curve is real and shifts up if base accuracy improves. At roughly 75% base instead of 57.6%, unanimity would land near 90% and the mid‑range settings would become defensible. Three untried levers, cheapest first.

  1. Refuse to answer on the dumping‑ground labels. The other team's model abstains 90% of the time when about to say service or utility. Targets the biggest measured defect directly. Hours of work.
  2. Signals nobody has fed in. Call‑graph data already computed — 6,277 functions with export flags — orders sensibly by archetype (route‑handler 0.30 → schema 0.86). Free, sitting unused.
  3. Richer content features. The current ones are deliberately cheap: hashed word counts plus pattern matches, no real code parsing.
Credibility

What we did not test, and what we got wrong

Included deliberately. A findings report that lists only its strengths is harder to trust than one that names its gaps.

Not tested

  • The head‑to‑head comparison the plan called for. Content features vs. path‑only features on identical data was never run. The project's own success criterion is therefore unmet, not failed.
  • Whether batching hurts Claude's accuracy.
  • Whether the ELM's disagreements are actually worse. Since the teacher is only 72.3% right, some may be improvements. Unmeasured.
  • The per‑call‑site token breakdown.

Sample sizes are thin. Most results rest on 69–260 evaluation rows. One promising early result (AUC 0.693) vanished under a more rigorous protocol (0.644). That is a caution about all of these numbers.

Mistakes made and corrected

  • An 80.4% accuracy figure was measured on the model's own training data — meaningless. Real figure: 52–67%.
  • A “40% token reduction” claim matched no measured result.
  • An automated “best setting” calculator optimised only for money saved, and therefore recommended never calling Claude at all.
  • The other team's published logs end with an automated verdict that printed “it collapsed” regardless of results. They fixed it and published a correction — but anyone skimming those logs draws the wrong conclusion.
